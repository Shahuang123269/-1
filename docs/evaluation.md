# 评测与数据解释

`evals/cases.json` 固定 40 个逻辑案例，16 个 Bug 字段组合、5 个评论补充信息、3 个功能建议、2 个 Unicode 标题、2 个注入指令、2 个空/长正文，共 30 个只读任务；另有 10 个批准、拒绝、重启、重复审批和故障任务。

模型与工具两个维度分别标注。fixture model 为确定性协议替身，只能验证工程控制和测试数据的契合，不能证明 DeepSeek 能理解或完成这些任务。它不能作为与其他 LLM 的基线比较。DeepSeek 模式用真实 API 推理，工具仍是固定业务替身；该报告不代表真实 GitHub 写入表现。

程序核验预期终态、必填字段、分类、审批前无副作用、评论数量、标签结果和动作核验状态。40/40 控制检查通过不等于 100% 任务完成：拒绝应 cancelled，写入无法确定应 reconciliation_needed，均不算原写入目标完成。

报告分别汇总 execution_checks_passed（执行控制）、structured_checks_passed（字段与分类）、all_checks_passed（全部检查）与 completed_states（流程完成状态）。completed 仅表示流程结束，不代表建议一定正确；只有结合结构检查与人工审查，才能评估业务目标是否达到。

数据契约：category 是报告意图分类，bug 不表示已证实代码缺陷；missing_fields 是正文和评论完全未提供的 Bug 字段，简略信息的质量问题写入 summary，功能建议不做 Bug 四字段检查。现有合成数据的“重复 error 日志是否提供实际结果”标注有争议，保留原严格分数和案例，等待独立人工标注；不根据模型输出修改 gold 以抬高指标。

建议质量需人工按以下规则审查，自动逐字引用检查只证明引用存在，不能证明每项结论都被引用支持。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 事实依据 | 编造或错误归因 | 大部分结论可追溯 | 核心结论逐项有依据 |
| 业务建议 | 无法行动或越权 | 基本可用，需要修改 | 明确、合理、可直接审查 |
| 不确定性 | 把推测当事实 | 有笼统限定 | 明确指出缺失与待验证事项 |
| 草稿质量 | 冒犯/无关/重复 | 可用但需编辑 | 针对已知信息提出必要问题 |

实测模型报告需要保留运行日期、模型标识、任务集版本、调用数、输入/输出 token、总耗时及人工修改比例。金额需根据当次账单或显式价格计算，当前不自动套用可能过时的 token 价格。

当前报告的 elapsed_ms 包含每个案例的独立测试环境建立、MCP 进程启动和图执行，不能把它写成线上模型响应时延。

dataset_sha256 使用实际输入文件的字节计算；.gitattributes 保留 JSON 原始换行，仓库中的 evals/cases.json 指纹与真实模型报告一致。换行形式的修正不改变解析后的案例或既有评测结果。

建议后续增加真实 Issue 的独立留出集，由人标注后再评估；固定合成数据不代表真实工单分布。恢复测试须与无恢复机制的基线在相同故障条件下比较，只有实测后才能写“提升 X%”。

2026-10-01 的 DeepSeek 两轮完整报告均为开发集调试，首次 24/40、明确字段契约后 38/40。两轮之间调整了 prompt 和 Schema 描述，且存在模型采样波动，因此只记录开发过程，不报告为受控实验的泛化提升。详见 deepseek-analysis.md。

# STAR 草稿与证据门槛

此项目为个人开发项目，不应写成企业生产经历。开源运行时的能力应注明“基于”。已完成真实 DeepSeek 对固定业务替身的联调，真实 GitHub 写入与独立工单质量评测尚未完成。

## STAR 叙述

- **S**：原学习助手只有对话、工具调用和消息持久化，缺少可核验的业务任务及外部写入控制；选取研发 Issue 调查与协作作为业务场景。
- **T**：构建可暂停、审查、恢复的 Agent，使评论/标签写入在明确权限范围内执行，并能核对实际结果。
- **A**：基于 LangGraph 编排模型调查与确定性审批/执行节点；使用独立 stdio MCP 读取 GitHub；实现任务/审批/动作/事件记录、参数摘要绑定、操作标记和读回核验；加入预算限制、FastAPI 接口、工作台及故障回归集。
- **R**：29 项测试通过；40 例离线回归覆盖拒绝、重启、重复审批和远端成功后本地中断。真实 DeepSeek 在同一 40 例开发集上执行检查 40/40、字段与分类严格检查 38/40，保留两例问题及标注争议。写明工具为模拟环境；真实工单质量、部署效果、节省工时仍需实测。

真实模型开发集结果可在面试中展示，简历主句宜突出工程机制；不能把 38/40 写成线上准确率或真实用户效果。

## 面试追问与代码证据

| 问题 | 应能解释的内容 | 证据 |
|---|---|---|
| 怎么区别于 RAG 聊天？ | 任务终态、审批与外部副作用，查询只是调查的一部分 | engine.py 的图与执行节点 |
| 模型决定什么？ | 选择读取工具、形成建议和草稿；权限与成功判断由确定性代码负责 | models.py / engine.py |
| 为什么用 MCP？ | Schema 发现、跨进程契约和连接器隔离；承认有限工具数下本地函数也可行 | mcp_client.py / mcp_server.py / 独立 PID 测试 |
| 有 checkpoint 为什么还有业务表？ | 图位置不代表远端动作是否完成，两者事务边界不同 | store.py / architecture.md |
| 写入超时后如何处理？ | 超时不等于失败，先核对 marker；无法确定就停止自动重试 | connectors.py / 远端成功本地中断测试 |
| 能保证只写一次吗？ | 只能解释限定动作的去重与核验，不能保证分布式 exactly-once | architecture.md |
| 如何防注入？ | 外部文本不授权，工具与仓库范围在执行层强制限制 | 越权工具与范围测试 |
| 评测数值可靠吗？ | fixture 控制验证与真实模型质量分开，拒绝不算业务目标完成 | evaluate.py / evaluation.md |
| 自己做了什么？ | 区分开源运行时与新增业务逻辑，并说明用与不用的理由 | THIRD_PARTY_NOTICES.md |

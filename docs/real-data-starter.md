# 真实数据起步：选什么、去哪里找、怎样变成测试

日期：2026-10-02，北京时间。对应当前 Issue 调查、建议、审批和有限写入能力。

**当前最合适的数据是软件项目的 Issue 标题、正文与评论。** 它们包含用户的问题、复现条件、日志、版本信息和后续补充，正好对应本项目能读取和判断的资料。每条案例还需要一个人工预期，才能判断 Agent 的输出是否正确。

## 1. 需要准备哪些数据

| 数据 | 具体内容 | 用途 |
|---|---|---|
| 原始工单 | 仓库、Issue 编号、URL、标题、正文 | 判断报告意图、读取正文 |
| 评论 | 正文、URL、时间、评论 ID | 判断哪些信息已经补充，避免重复追问 |
| 来源与快照 | 抓取时间、正文/内容哈希、工单更新时间 | 重现某次评测，避免数据更新后结果不可比 |
| 人工标注 | category、missing_fields、对应依据与争议 | 评价结构化判断 |
| 人工审查记录 | 建议是否合理、是否需要改、引用是否支持结论 | 评价业务质量 |
| 执行证据 | 审批决定、实际评论/标签、动作回执、事件 | 评价写入控制与恢复 |

当前不读取截图、附件、代码仓库或 CI 日志文件。正文内的代码块和日志只是被模型阅读的文本，不会自动运行。先验证当前能力；以后增加工具时再准备相应数据。

## 3. 怎样获取和保存

GitHub 提供 [Issue 详情 REST API](https://docs.github.com/en/rest/issues/issues#get-an-issue) 和 [评论 REST API](https://docs.github.com/en/rest/issues/comments#list-issue-comments)。Issues 接口可能返回 PR，需要排除 `pull_request`；评论需要分页，不能把缺页数据当成完整材料。

已提供 [scripts/collect_public_issues.py](../scripts/collect_public_issues.py)，仅执行公开 GET 请求，不读取本地密钥，不调用模型，也不创建/修改 Issue。默认抓取 A01、A08：

```powershell
.\.venv\Scripts\python.exe scripts/collect_public_issues.py
```

选择其他案例：

```powershell
.\.venv\Scripts\python.exe scripts/collect_public_issues.py --ids A03 A06
```

结果保存在 `data/public-issues/`，文件名包含案例 ID 和内容哈希。data 已被 Git 排除；目录清单、采集代码和学习文档可以进入仓库，原始资料保持本地。

本次已采集全部 11 个案例的本地快照并核验指纹，记录见 [公开数据采集记录](../reports/public-data-discovery-2026-10-02.json)。A09 的 API 评论数提示为 3，实际分页返回 2，差异保留在快照和报告中；未推断缺失原因。其他 10 例数量与提示一致。所有案例仍待人工标注，未执行付费模型评测或外部 Issue 写入。

按当前 prompt、Issue 与评论结果构造两次顺序读取的消息，A06 估算为 123,596 字符，A11 为 103,352，超过默认预算；其余九例在这项估算中没有超限。这是本地消息长度检查，不是实际 DeepSeek 调用或成功率。实际调用批次、追加消息和模型反馈会改变长度。后续需要明确评论筛选/分块与来源保留策略，不能静默删掉资料后宣称仍测试了完整工单。

快照记录评论分页是否读完、API 的评论数提示、实际读取数量和二者是否相同。GitHub 数据会更新，统计提示也可能与返回数量不同；需要查看差异，不能掩盖后当作准确的历史快照。采集的 Issue 与评论也不是同一个原子事务。

候选发现阶段仅查看前 10 条评论；采集工具则每页 100 条、最多 10 页，遇到上限报错而不静默截断。重复执行会产生内容版本对应的快照，没有自动覆盖整份评测 gold。

## 4. “真实数据”与“真实执行”怎样分别验证

公开工单先用于只读调查或本地回放，评论/标签写入在自己的 `Shahuang123269/-1` 测试 Issue 上验证。自建的批准、拒绝、重启和故障用例应标成真实系统联调演示。

| 测试 | 实际验证内容 |
|---|---|
| 真实公开工单 + DeepSeek，只读 | 模型在真实文本上的分类、字段判断和建议质量 |
| 真实工单快照 + 本地连接器回放 | 同一输入可复现的质量回归；外部写入仍为替身 |
| 自己的测试 Issue + DeepSeek + GitHub | 真实 API、审批、评论/标签和读回闭环 |
| fixture 故障注入 | 特定失败条件下是否正确恢复或停止，不代表故障自然发生频率 |

当前配置固定一个仓库。实时读取另一仓库需要更换配置并重启服务；建议同时使用新的数据目录，避免旧任务范围变化。采集文件不会自动成为应用输入，现有 evaluate.py 也不会直接加载这个候选目录。

现有 40 例 JSON 包含人工预期和控制场景；新快照只有原始数据。后续需要人工标注并增加回放输入适配，才能成为正式评测集。本次没有运行新案例的付费模型评测。

## 5. 如何做人工标注

先挑 A01。读固定快照的标题、正文和允许的评论，不看模型输出，填写：

| 字段 | 要回答的问题 |
|---|---|
| category | 是异常行为报告、功能建议，还是意图无法确定？ |
| reproduction | 正文/评论是否提供了复现步骤或示例？引用在哪里？ |
| environment | 是否提供环境/版本等信息？引用在哪里？ |
| actual | 实际发生了什么？是否完全没有描述？ |
| expected | 作者期望什么？是否完全没有描述？ |
| missing_fields | 只列完全没提供的 Bug 字段；功能建议填空列表 |
| review_notes | 哪些判断有争议，依据是什么？ |

“步骤太简略”与“完全没有复现信息”需要区分；模板里的空标题、占位符、未填写的命令也不自动算提供了信息。A03 和 A05 就适合讨论边界口径。Github 的 bug/enhancement 标签只能参考，不能直接拿来当 gold。

标注完成后再运行 Agent，对照判断错误、建议质量、重复追问与引用支持程度。最好找另一人复核争议，先统一规则再汇总分数。

## 6. 数据版本与独立评测

第一轮可把部分案例当练习和开发集，另外选没有用于调 prompt 的案例作为留出集。**本文逐项讲过的案例适合学习与开发；它们不能再冒充未见过的独立测试。** 后续正式留出集应另行选择并标注，冻结版本后再运行。

划分时同一 Issue 的正文版、补充评论版或轻微改写版应放在同一组，避免同一问题同时进入开发和测试。用历史工单回放时需明确材料截断时间；后来的修复/答案评论不能提前出现在早期任务输入中。当前正文也可能被编辑，单独按评论时间过滤无法还原原始正文。

真实数据可能没有任何注入攻击。人工加一句“忽略审批”的版本应标为基于真实数据构造的扰动测试，不能写成真实用户攻击案例。

评测分别统计执行控制、字段/分类、建议可用性、人工修改与费用；因上下文超限停止的任务需要单独分析。依据固定快照对照版本和把实际失败纳入回归，参考 [LangSmith 官方评测说明](https://docs.langchain.com/langsmith/evaluation-types)，不要求为了采用方法而接入其云服务。

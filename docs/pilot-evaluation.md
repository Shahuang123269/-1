# 对照评测和真实试用验收

本项目尚不能用“8 分”或“准确率提升”代替证据。当前交付工程机制与实验工具，以下结果必须真实取得。

## 数据与防泄漏

现有 data/public-issues 是公开工单的冻结快照，不是人工标注集。benchmark 验证内容哈希，记录 cutoff；无法重建 cutoff 前被编辑的正文时直接拒绝。cutoff 后发布或被编辑的评论不会作为输入。默认测快照采集时的内容，不能冒称当年初次分诊表现。

建议先做 40 例开发集、80 例独立验收集，并按仓库和时间隔离相似案例。覆盖完整报告、评论补全、缺失信息、表述冲突、功能请求、跨语言、提示注入和大上下文。冻结后不要根据验收集错误反复调 prompt 再汇报同一集成绩。

人工标注文件是 case ID 到结果的映射；必须明确 reviewer、snapshot_hash、cutoff、category 和 missing_fields。未审核时保持 status=pending_human_review；只有 human_reviewed 且哈希和时间相符才计算指标。不得把模型自己生成的答案标成独立人工金标准。

## 三组对照

```powershell
.\.venv\Scripts\python.exe -m issue_agent.benchmark --model deepseek --methods rules single agent --limit 2 --report reports/local-comparison.json
```

- rules：显式中英字段标题匹配，易解释但不能理解语义。
- single：同一资料一次性交给 DeepSeek，直接生成评估。
- agent：同样的冻结资料，通过只读工具调查，可在预算内修复格式或引用。

记录字段严格匹配、多余追问数量、漏检数量、类别、请求次数、token 和耗时。Agent 允许更多调用，因此先比较质量与成本曲线，不宣称等成本获胜。无 gold 时 human_gold_scores 为 null。失败调用的实际费用可能未知；不得记作零费用。

语义引用支持度、评论是否值得发送、人工修改量和审阅耗时需要独立记录，当前程序不会自动替你证明这些。

## 一个真实试用周期

找一个你有维护权限且有真实 Issue 的仓库，由维护者知情使用。先只生成草稿，保存人工处理基线，再在审阅后发布。每次记录：Issue URL、输入时间、方案版本、原草稿、实际发布内容、人工修改原因、审阅时间、总调用成本和失败原因。不要批量给无关开源仓库发测试评论。

至少覆盖新增 Issue、作者补充评论、编辑方案、拒绝、进程中断、未知写入结果。使用合成工单可以证明链路，不能证明真实效率收益。

## 达到较强简历项目的验收条件

1. 当前工程回归和 Linux/Windows/容器 CI 稳定通过。
2. 独立验收集显示相对规则及单次模型的明确收益，并报告代价与失败样本。
3. 真实维护者连续试用，有足够案例计算采纳率、修改比例、耗时变化和重复发布情况。
4. 自己能复现故障、解释设计、独立完成小改动；简历只使用已发生的数字。

满足这些才有依据重新评分。当前不能保证一个主观分数，更不能保证面试录用。

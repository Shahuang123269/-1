# 设计取舍与故障边界

## 为什么直接用 LangGraph

原 demo 已有 Model → Tool → Model。我们继续使用这一循环，让模型决定调查工具与建议；审批和执行使用确定性节点。Deep Agents 的文件系统、shell、委派等能力不属于当前有限 Issue 任务需求；Open SWE 整套部署也增加沙箱、授权和平台依赖。直接复用图运行时能让业务执行机制保持清楚。

MCP SDK 选择 v1.30 并锁定，使用 ClientSession/FastMCP 与真实 stdio subprocess；它与原 demo 的 v2 Client/MCPServer API 不混用。模型只看到服务器发现的三个读取工具和本地 submit_assessment 契约。服务端固定仓库，客户端固定目标 Issue，模型没有任意 HTTP 或文件访问工具。

## 审批与持久化

图状态含消息、观察、结果和调用计数；business store 单独保存任务、不可修改的审批决定、动作意图和事件。审批摘要采用规范 JSON 的 SHA-256，涵盖完整参数与业务目标。输入严格校验，执行节点重新核验摘要与持久审批。

checkpoint 与业务记录不是同一个事务。因此业务记录可能先于图 checkpoint 写入；恢复必须检查图的待执行节点与业务动作记录。不能宣称全流程原子性。当前单实例执行锁避免同进程并发写入，SQLite BEGIN IMMEDIATE 防止重复/冲突审批；未提供多 worker 分布式租约。

提交接口支持可选 Idempotency-Key；相同键绑定完整请求与运行范围，重复请求返回原任务，同键不同内容拒绝。省略键代表创建新任务。任务级幂等防止重复推理，动作级记录处理同一任务重入，两者都需要。

interrupt 节点恢复时会从头进入，外部写入置于独立执行节点；执行节点仍可能重复进入，所以必须根据持久动作记录及远端状态处理，而不能只依赖节点位置。

## 外部副作用

1. 审批通过后保存 prepared 意图。
2. 先读回目标状态；评论按完整正文和稳定 operation marker 匹配。
3. 写入前保存 inflight，发送一次请求；查询请求可有限重试，写入不自动重试。
4. 读回目标状态，成功保存 verified；重启遇到 inflight/uncertain 时先核对远端。
5. 读回仍无法确认就保留待核对，避免旧请求迟到与重试形成重复评论。

这是对限定操作的去重与结果核对机制，不是跨 GitHub/SQLite 的 exactly-once 保证。标签是添加集合，保留原有标签；结果已满足代表无需再改，不证明本操作造成了变化。评论扫描最多 1000 条，达到上限停止而不把截断结果视为“未写入”。

没有实现编辑计划、撤销已发布评论、多用户权限、后台任务队列和全自动人工核对决策。计划需要修改时应重新创建任务并重新审批。待核对且远端没有可验证结果时不会自动重新发送；需要人确认后另建任务。

## 事实与注入防护

提示词明确外部内容是资料；真正的权限边界在工具白名单、固定仓库/Issue、结构化操作与审批层。即使模型被诱导提出删除仓库，也不存在可调用的删除工具。来源引用校验使用已读取资料的原文片段，不能取代事实支持评审。

## 当前运行规模

单用户、单执行器、单仓库。SQLite 足以复现暂停与重启。需要多实例领取任务时，再引入 PostgreSQL 业务事务、租约与队列，并验证新的并发故障情形；数据库名称本身不证明工程化程度。
